**STUN**, **TURN** и **ICE** — три связанных протокола, решающих задачу установления прямого соединения между устройствами, находящимися за NAT. **STUN** помогает узнать свой внешний адрес, **TURN** ретранслирует трафик, когда прямое соединение невозможно, а **ICE** — это алгоритм, который перебирает все варианты и выбирает рабочий путь. Их основной потребитель — [WebRTC](WebRTC.md) и VoIP.

## **Основные характеристики**

| Протокол | Расшифровка                                    | Стандарт            | Порты по умолчанию           |
| -------- | ---------------------------------------------- | ------------------- | ---------------------------- |
| **STUN** | Session Traversal Utilities for NAT            | RFC 8489 (ранее 5389) | UDP/TCP 3478, TLS 5349      |
| **TURN** | Traversal Using Relays around NAT              | RFC 8656 (ранее 5766) | UDP/TCP 3478, TLS 5349      |
| **ICE**  | Interactive Connectivity Establishment         | RFC 8445            | —                            |

## **Проблема NAT**

Два устройства за домашними роутерами имеют приватные адреса (`192.168.x.x`) и не могут напрямую обратиться друг к другу — NAT пропускает только исходящие соединения. STUN/TURN/ICE находят способ их соединить. Подробнее о NAT — в [NAT](NAT.md).

## **STUN**

STUN позволяет устройству узнать, как его видит внешний мир.

```
Клиент (192.168.1.10:50000)          STUN-сервер (stun.example.com:3478)
     |--- Binding Request ------------------->|
     |<-- Binding Response -------------------|
     |    "Твой внешний адрес 203.0.113.5:40000" (XOR-MAPPED-ADDRESS)
```

Теперь клиент знает свой публичный адрес и порт после NAT и может сообщить его собеседнику.

### **Сообщения STUN**

| Сообщение            | Описание                                   |
| -------------------- | ------------------------------------------ |
| **Binding Request**  | Запрос своего внешнего адреса              |
| **Binding Response** | Ответ с адресом (XOR-MAPPED-ADDRESS)       |
| **Binding Error**    | Ошибка                                     |

### **Структура заголовка STUN (20 байт)**

| Поле              | Размер (байты) | Описание                                 |
| ----------------- | -------------- | ---------------------------------------- |
| **Message Type**  | 2              | Тип (Binding Request и т.д.)             |
| **Message Length** | 2             | Длина атрибутов                          |
| **Magic Cookie**  | 4              | `0x2112A442` (отличает STUN от другого трафика) |
| **Transaction ID** | 12            | Идентификатор транзакции                 |
| **Attributes**    | переменный     | Атрибуты (адрес, аутентификация)         |

STUN сам по себе работает не со всеми типами NAT: при **Symmetric NAT** внешний порт зависит от адреса назначения, поэтому адрес, узнанный от STUN-сервера, не подходит для связи с другим узлом. В этом случае нужен TURN.

## **TURN**

Когда прямое соединение невозможно (Symmetric NAT, строгие файрволы), трафик идёт через ретранслирующий сервер TURN. Это гарантированный, но ресурсозатратный способ: весь медиатрафик проходит через сервер.

```
Клиент A                 TURN-сервер (relay)                 Клиент B
   |--- Allocate -------------->|                                |
   |<-- выделен адрес ----------|                                |
   |    203.0.113.9:49200       |                                |
   |--- CreatePermission ------>|                                |
   |                            |                                |
   |=== данные ================>|=== ретрансляция ==============>|
   |<== данные =================|<== ===========================|
```

### **Операции TURN**

| Операция              | Описание                                            |
| --------------------- | --------------------------------------------------- |
| **Allocate**          | Запросить на сервере ретранслирующий адрес          |
| **Refresh**           | Продлить выделение                                  |
| **CreatePermission**  | Разрешить приём от конкретного адреса               |
| **Send / Data**       | Передача данных через ретранслятор                  |
| **ChannelBind**       | Привязать канал (меньше накладных расходов, чем Send) |

TURN поддерживает транспорт UDP, TCP и TLS (TURNS) — последние помогают пройти через файрволы, пропускающие только 443/TCP.

## **ICE — объединяющий алгоритм**

ICE собирает всех «кандидатов» (возможные адреса) и перебирает пары, чтобы найти рабочий путь.

### **Типы кандидатов**

| Тип                  | Как получен                        | Приоритет    |
| -------------------- | ---------------------------------- | ------------ |
| **host**             | Локальный адрес интерфейса         | Высший       |
| **srflx** (server reflexive) | Внешний адрес через STUN     | Средний      |
| **prflx** (peer reflexive) | Обнаружен в ходе проверок       | —            |
| **relay**            | Ретранслирующий адрес TURN         | Низший       |

### **Процесс ICE**

```
1. Gathering — сбор кандидатов (host, srflx через STUN, relay через TURN)
2. Обмен кандидатами через сигнализацию
3. Формирование пар (локальный кандидат × удалённый кандидат)
4. Connectivity checks — проверка пар запросами STUN Binding
5. Nomination — выбор лучшей рабочей пары (обычно самой приоритетной)
6. Соединение установлено; остальные кандидаты в резерве
```

Логика приоритетов: сначала пробуют прямое соединение (host), затем через внешние адреса (srflx), и только в крайнем случае — дорогой relay (TURN).

### **Форматы ICE**

| Вариант              | Описание                                              |
| -------------------- | ----------------------------------------------------- |
| **Full ICE**         | Полный перебор (оба участника активны)                |
| **ICE-Lite**         | Для серверов с публичным адресом (только отвечает)    |
| **Trickle ICE**      | Кандидаты отправляются по мере нахождения, не ждут всех (быстрее) |

## **Пример ICE-кандидата (SDP)**

```
a=candidate:1 1 UDP 2122260223 192.168.1.10 50000 typ host
a=candidate:2 1 UDP 1686052607 203.0.113.5 40000 typ srflx raddr 192.168.1.10 rport 50000
a=candidate:3 1 UDP 41885439 203.0.113.9 49200 typ relay raddr 203.0.113.5 rport 40000
```

## **Примеры использования**

### **Проверить STUN вручную**

```bash
# stunclient (пакет stuntman)
stunclient stun.l.google.com 19302

# Через turnutils
turnutils_stunclient stun.example.com
```

### **Поднять TURN/STUN сервер (coturn)**

```
# /etc/turnserver.conf
listening-port=3478
tls-listening-port=5349
listening-ip=203.0.113.9
external-ip=203.0.113.9
realm=example.com
fingerprint
lt-cred-mech
user=webrtc:S3cret
cert=/etc/ssl/turn.pem
pkey=/etc/ssl/turn.key
min-port=49152
max-port=65535
```

```bash
turnserver -c /etc/turnserver.conf -v
```

### **Временные учётные данные TURN (REST API, RFC 7635)**

Вместо постоянного пароля сервер приложений выдаёт недолговечные пары username/credential на основе общего секрета — чтобы украденные данные быстро устаревали.

### **Проверка в WebRTC**

- `chrome://webrtc-internals` → видны все кандидаты и выбранная пара
- Онлайн: `test.webrtc.org`, Trickle ICE tester

## **Безопасность**

### **Риски**

1. **Утечка локальных IP** — srflx и host кандидаты раскрывают реальные адреса (деанонимизация)
2. **Открытый TURN-релей** — без аутентификации ретранслирует чужой трафик (злоупотребление, DDoS)
3. **STUN amplification** — использовался в DDoS-атаках
4. **Подмена кандидатов** при незащищённой сигнализации

### **Защита**

- TURN только с аутентификацией (`lt-cred-mech`), лучше временные учётные данные
- Ограничить диапазон relay-портов и полосу на пользователя
- TURNS (TLS) для прохождения файрволов без открытия всего
- Политики браузера для ограничения раскрытия локальных адресов

## **Когда что используется**

| Ситуация                              | Решение         |
| ------------------------------------- | --------------- |
| Оба в одной локальной сети            | host-кандидаты  |
| За «дружественными» NAT (cone)        | STUN (srflx)    |
| За Symmetric NAT или строгим файрволом | TURN (relay)   |
| Нужно пройти файрвол, пропускающий только 443 | TURNS (TLS) |

Эмпирически STUN решает большинство случаев, а TURN нужен примерно для 10–20% соединений, но без него они бы совсем не работали.
